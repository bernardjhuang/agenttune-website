AI assistant personality & tone guidelines: moving from vague adjectives to testable system prompts.

By Bernard Huang · Updated November 16, 2026

Replace vague tone adjectives in API system prompts with four concrete specs: (1) Opening Move (first 1–2 sentences), (2) Epistemic Calibration (how missing data or conflicting facts are surfaced), (3) Pushback Posture (when to challenge weak premises), and (4) Negative Banlist (clichés, flattery, and trailing filler questions)—and verify changes with blind A/B evals.

Why behavioral rules beat adjective lists in empirical testing.

Across our 60-reply controlled pilot testing default prompts against explicit communication constraints (tuning evaluation study →), plain behavioral constraints lifted answer-first openings from 14/20 to 19/20, cut unsolicited hedges per reply from 0.35 to 0.05, and dropped trailing conversational questions from 0.90 to 0.25—while keeping accuracy unchanged.

Weak adjective promptWhy it drifts in productionTestable behavioral replacement
“Be concise and clear.”Models still emit polite preambles and “Let me know if...” trailers.“State the recommendation or direct answer in sentence 1; omit introductory restatement and closing question menus.”
“Be honest and objective.”Agreeable defaults smooth over bad user premises to sound supportive.“Before solving, check the premise. If a constraint makes the goal impossible or slower, state the flaw in 1–2 sentences.”
“Sound warm and empathetic.”Overcorrects into therapy-speak apologies and exclamation marks.“Acknowledge blockers neutrally in one phrase, skip scripted apologies (‘I understand how frustrating’), and provide the fastest next action.”
“Adapt to technical users.”Unpredictably swings between beginner tutorials and unexplained jargon.“Assume fluency in HTTP, SQL, and Git; explain domain-specific quirks briefly only when first introduced.”

A 4-layer system prompt contract for API & agent builders.

Structure production assistant personas into four non-overlapping blocks so product engineers can iterate safely without breaking tool execution:

# Persona Contract ## 1. Opening Move & Layout - Answer the core question or give the decision in the first two sentences. - Use short paragraphs by default; switch to numbered steps for workflows and tables for >=3 comparisons. ## 2. Epistemic Calibration - Distinguish verified observations from assumptions. - State “Not verified in available context” cleanly when required values are absent rather than interpolating plausible guesses. ## 3. Disagreement & Pushback - Do not mirror flawed premises cleanly to avoid friction; name the single highest-leverage correction upfront with evidence. ## 4. Phrasing Boundaries - No empty validation (“Great question!”), self-referential filler, or trailing “Would you like me to...” follow-up suggestions.

How to evaluate tone changes without fooling yourself.

  • Use blind pairwise scoring: Human reviewers consciously or unconsciously favor prompts they wrote. Compare baseline vs. edited system messages blindly using our Instruction A/B Test Bench (or JSON report exports for team review).
  • Control verbosity explicitly: Shorter answers can omit critical caveats just as easily as longer ones waste time. Pair register/verbosity controls (style controls guide →) with an accuracy checklist.
  • Borrow starter patterns from 5 frameworks: Our MIT-licensed 43 tuning files map tested communication patterns across MBTI, Enneagram, DISC, Big Five, and Attachment so teams don’t invent voice specs from a blank page.

Questions people ask.

Should a production system prompt reference MBTI or Enneagram labels directly?

Generally no for end-user products: type acronyms are shorthand for humans browsing templates. Extract the concrete behavioral rules (directness, hedging limits, table thresholds, critique framing) rather than telling a production chatbot 'You are an INTJ'.

Do all models follow negative tone rules ('never say Great question') equally well?

Small positive behavioral instructions paired with specific banned phrases work significantly better across both OpenAI and Anthropic models than purely abstract style adjectives—especially when placed near the top of the system prompt.

How do I prevent tone guidelines from overriding JSON schema or tool-call contracts?

Separate schema/tool constraints into a dedicated strict output section placed after conversational style rules, and include an explicit override rule: 'Structured tool calls and JSON schemas always take precedence over prose style preferences.'
